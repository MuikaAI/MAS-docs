# 架构概览

Muika-After-Story 将 Core、传输和聊天平台适配分开。Core 不依赖 NoneBot；`muika_bot` 负责 NoneBot 接入，其他平台也可以通过 WebSocket IPC 连接。

主人格与行动 Agent 属于同一个 Muika。对话、行动结果、日记和持续状态共同保存她与玩家的关系；重启和设备切换延续已有经历。

## 部署结构

单机模式下，适配器直接连接 Core：

```text
玩家 ↔ 聊天平台 ↔ 平台适配器 ↔ /ws ↔ Muika Core
                                      进程监督 → Core
```

多设备模式增加常驻聊天入口 Gateway：

```text
玩家 ↔ 聊天平台 ↔ 平台适配器 ↔ Gateway /ws
                                ├─ /cores ↔ 电脑 Core：本地记忆、工具和插件
                                └─ /cores ↔ 服务器 Core：本地记忆、工具和插件
```

入口在线时，一个活动 Core 负责对话和行动，备用 Core 同步已有结果。
各设备使用独立数据库；工具、任务目录和插件文件留在原设备。网络分区时，本地回退可能产生两段历史，重连后会保留两段经历。

`core_main.py` 启动独立父进程，监督 Core 的重启与启动失败恢复。Launcher 管理实例安装、配置、模型和 Core / Bot 进程；它与 Core 的父进程监督分工不同。

## 数据流

```text
聊天平台 ↔ Bot 适配器 ↔ WebSocket IPC ↔ Core
                                       ├─ 命令派发 → 命令结果
                                       └─ 事件队列 → Muika 事件循环
                                                    ├─ Brain：对话与主动发言
                                                    ├─ AgentTasks：后台行动与结果事件
                                                    ├─ TopicManager / DigestAgent：话题与阅读
                                                    └─ MemoryManager：经历、日记、事实和状态

对话回复 → Executor → IPC → Bot → 聊天平台
行动结果 → 事件队列 → Brain → 对话回复
```

Core 是单一主人的陪伴核心。适配器过滤输入，IPC 保留连接认证。普通消息进入事件循环，命令直接进入命令派发器。

## 组件职责

| 组件 | 职责 |
| --- | --- |
| `Muika` | 收集事件、推进即时状态、选择对话或话题流程 |
| `MuikaBrain` | 组装人格、持续状态、记忆与当前输入，生成回复 |
| `Agent` / `AgentTasks` | 组装行动提示，保存任务与工具记录，处理继续、纠正、取消和恢复 |
| `MemoryManager` | 保存原始素材、日记、事实版本、持续情绪及工作摘要 |
| `MemoryReasoner` / `ReflectionAgent` | 检索相关记忆，调度每日整理与补做 |
| `TopicManager` / `DigestAgent` | 选择主动话题，从 RSS 形成阅读笔记 |
| `Executor` | 分段发送文本和资源 |
| `CoreWsServer` | 认证适配器连接，转换 IPC 消息 |
| `Gateway` / `CoreLink` / `SyncStore` | 协调活动设备，保存与同步真实活动，并映射各设备本地记录 |
| `SelfChangeLedger` / `SelfChangeDispatcher` | 持久化内核和插件变更，合并事件并控制感知节奏 |
| `Code Review Agent` | 根据行动权限和审查模式检查代码操作 |
| `muika.ipc.supervisor` | 启动 Core 子进程，处理重启请求和自改后的启动失败恢复 |

## 事件循环

Core 等待队列事件；等待 5 秒仍无输入时产生 `TimeTickEvent`。

| 触发条件 | 处理方式 |
| --- | --- |
| 用户消息 | 保存原文与资源，检索相关记忆，再生成回复 |
| 会话启动 | 区分首次见面与回归，使用已保存的关系和经历 |
| 定时提醒 | 将提醒交给主人格处理 |
| 行动结果 | 核对任务修订号，保存真实结果，再交给主人格回应 |
| 设备变化 | 提供活动设备与可用设备事实，由主人格决定是否回应 |
| 内核或插件变化 | 合并外部变更事实，保留归因和版本信息，交给主人格感知 |
| 未处理意愿与持续失衡 | 满足空闲条件和主动冷却后进入思考 |
| 孤独、无聊或好奇 | 在对应条件满足时触发对话或话题流程 |
| 普通空闲 | 推进状态，并检查日记与阅读等后台工作 |

非 `time_tick` 事件均记录 INFO。重复时间事件、模型计时和详细执行信息记录 DEBUG。

## 说话与行动属于同一个 Muika

Brain 负责她在对话中的表达，Agent 是她的行动半身。执行较长任务时，用户仍可继续聊天。

1. Brain 的回复可以包含私有 `<memory>`、`<state>` 和 `<agent>` 标签。
2. 记忆笔记保存为待整理素材，状态更新保存她的情绪和意愿。
3. 行动指令交给持久任务；一个任务执行时，其余任务排队等待。
4. 后续纠正、继续与取消进入已有任务，在动作边界生效。
5. 工具结果和执行检查点保存后，结果事件回到 Brain，由她自然地回应用户。

完成行动不等于收到正面反馈。任务回报不会重开她已解决或已放下的意愿；她仍可主动改变决定。
行动能力由 `ACTION_PERMISSION` 和授权路径决定，代码操作使用既有审查流程。
`self_modify` 开放人格、技能、话题、插件修改和 Core 提案；Core 提案经过验证与审查后，才进入应用、重启和恢复流程。
配置方式见[行动范围](/guide/configuration#行动范围)。

## 会话、日记与重启

原始对话和行动结果逐轮保存。新会话只切换工作上下文，不会重新开始关系，也不即时生成日记。
本地时间 05:00 后的空闲阶段整理前一天，启动和空闲时补做积压日期。`.reflect` 可手动整理今天已有素材。

记忆系统保留日记、事实来源、最早已知互动日期和持续状态。行动任务保存检查点，重启后核对现场并恢复。
单机模式的提醒保存在内存中。多设备模式保存提醒，并只在活动 Core 上运行。

## 自身变更感知

启动时对比内核、版本和用户插件指纹；运行时记录成功的外部插件重载或卸载。
检测先写入持久账本，投递再等待编辑沉降、最小间隔和可用连接，避免频繁保存触发连续发言。

合并的 `SelfChangedEvent` 携带修改、更新、升级或降级的事实。具体事实和表达余裕进入当前轮的 Brain 提示，Muika 自行决定如何回应；人格系统提示不随批次改写。
她自己的部署、回滚和经核对的自改重启推进基线；玩家命令重载记录已知操作，不作为突然发现的外部变更。

传输成功或她选择沉默后，先幂等写入记忆，再清除对应账目。仅进入离线发送队列时继续保留账目；发送或记忆写入失败会重试。
感知设置见[自身变更感知配置](/guide/configuration#self-change)。

## 可选的多设备运行

各 Core 使用独立本地数据库、工具和插件。Gateway 保存活动日志和收到的输入，按连接活性、优先级和任期选择在线活动 Core。
`CoreLink` 通过 `/cores` 交换历史与活动角色；Bot 继续使用原有 `/ws` 协议。

业务提交产生 `Activity`，保存真实经历、事实、日记、任务结果、持续状态与提醒。来源编号映射到各 Core 本地主键。
备用 Core 应用已保存结果，不重新推导模型输出、不重做工具调用。空闲时间状态按实际经过时间本地推进，不复制 tick。

输入事件与输出事件相互独立。沉默和主动发言都有效；输出不要求绑定输入，也不增加平台投递确认。
被中断的远端执行记录为失败，原设备仍可能留下副作用。重连不重发旧输出，不恢复远端进程。

网络分区时，指定 PC 可以本地继续活动。重连保留两段历史，前台 PC 保留当前状态。
共同日志中的位置只表示同步进度。Gateway 失联不会强制指定 PC 拒绝本地服务。

聊天附件使用认证后的 `/attachments/{sha256}` 上传和下载。线上引用为相对路径，各设备使用自己的入口地址。
这不是通用文件访问接口，任务目录和插件文件不会迁移。部署操作见[多设备部署](/guide/multi-device)。
